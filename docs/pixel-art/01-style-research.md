# 01 現況調查與像素風格研究

日期：2026-11-17
範圍：只做調查與研究，沒有修改任何既有程式。

每一項結論都標上來源等級：

| 標記 | 意思 |
|---|---|
| 【觀察】 | 直接從程式碼或參考圖看到的 |
| 【量測】 | 從參考圖的像素資料算出來的數字，附量測方法 |
| 【推論】 | 由觀察或量測推出來，沒有直接證據 |
| 【提案】 | 給本專案的建議，需要使用者決定 |
| 【未驗證】 | 找不到可靠來源，或來源沒有讀到原文 |

## 第一部分：本專案現況

### 1. 語言、繪製技術、框架【觀察】

- 後端：Node.js（≥20.12）ESM，沒有第三方執行期依賴。
- 前端：Svelte 5 + Vite 8，測試用 Vitest 與 @testing-library/svelte。
- 沒有遊戲引擎，也沒有 canvas。畫面是一般的 DOM 加 CSS，角色是行內 SVG。
- 專案裡沒有 C#/.NET。

### 2. 現有的像素繪製方式【觀察】

- `web/src/lib/sprite.js`：角色是 12×16 的字元格（一個字元代表一種部位顏色）。髮型與頭飾用「覆寫指定列」疊上去，再把同一列相鄰同色的格子合併成橫條。
- `web/src/components/PixelArt.svelte`：把 `{ width, height, rects }` 畫成 `<svg>`，每個橫條是一個 `<rect>`，設定 `shape-rendering="crispEdges"`。
- `web/src/components/HallScene.svelte` 與 `web/src/styles/pixel.css`：吧檯、酒瓶、桌子、沙發、空椅子全部是 CSS 方塊（背景色加 3px 邊框），不是點陣圖。
- 造型由使用者編號當種子（mulberry32）決定：髮型 5 種、頭飾 6 種、髮色 6、膚色 4、衣服 8、配件色 5。

### 3. 尺寸與像素密度【觀察】

| 項目 | 原生格數 | 畫面大小 | 一格等於幾個 CSS 像素 |
|---|---|---|---|
| 場景角色 | 12×16 | 36×48 | 3 |
| 名單小角色、窄螢幕角色 | 12×16 | 24×32 | 2 |
| 狀態圖示 | 7×7 | 14×14（外框 22×22） | 2 |
| 家具與邊框 | 無格線 | 邊框 3px、陰影 3–4px | 約 3，但尺寸是任意值 |
| 文字 | Cubic 11 點陣字 | 12px、24px | 字型自己的格線 |

【推論】畫面上同時有 2 倍與 3 倍兩種密度，家具又不在任何格線上，這是目前看起來不一致的主因之一。

### 4. 座標與視角【觀察】

- 沒有世界座標，也沒有鏡頭。位置完全由 CSS grid 決定，位子編號（例如 `desk-3`）對應到格子。
- 角色是正面平視；家具是平面色塊，沒有頂面與正面之分。場景沒有統一的投影方式。
- 沒有深度排序，前後關係就是 DOM 順序。角色永遠畫在自己的格子裡，不會被桌子遮住。

### 5. 圖片資產與動畫格式【觀察】

- 沒有任何點陣圖資產。`web/src/assets` 只有字型，`web/public` 只有 `favicon.svg`。
- 沒有動畫格式。唯一的動態是滑鼠移上去時角色往上 3px（CSS `transform`）。
- 角色只有一個影格；「休息」是把眼睛換成暗膚色。

### 6. 縮放與濾鏡【觀察】

- 縮放靠 SVG 的 `viewBox`，目前都是整數倍，所以邊緣銳利。
- 沒有用到 `image-rendering`，因為沒有點陣圖。
- 陰影色由 `darken()` 把 RGB 乘 0.7 得到，只有衣服有一階暗部，沒有亮部，也沒有色相偏移。

### 7. 資產管理與載入【觀察】

- 沒有資產清單、沒有載入器、沒有版本。造型在每次繪製時由純函式即時算出。
- 圖示（槌子、三個點、Z）直接寫在 `sprite.js` 裡。

### 8. 架構限制與整合風險

- 【觀察】CSP 是 `default-src 'self'`，建置設定 `assetsInlineLimit: 0`。不能用 `data:` 或 `blob:` 圖片，元件不能有 inline style、`style:`、`transition:`。
- 【觀察】成員是用名稱搜尋後才加入，建置時不知道會有哪些使用者編號。
  【推論】角色必須在瀏覽器即時產生，不能每人預先做一張 PNG，也不能在執行時呼叫 AI。
- 【觀察】角色是 `<button>`，有 `aria-label`、`aria-pressed`，多個測試依賴這個結構與 `data-seat`。
- 【觀察】`lookFor()` 的抽選順序固定。【推論】只要改動產生器，所有人的造型都會換掉。
- 【觀察】專案原則是簡單優先、沒有執行期依賴；`web/src/lib/api.js` 是唯一呼叫 `/api` 的模組。
- 【推論】最大的整合風險是場景：要做出有前後遮擋的 3/4 視角，場景得從「CSS 方塊排版」改成「有錨點與圖層順序的圖塊」，同時保住按鈕結構與無障礙名稱。

## 第二部分：Tiny Pixel Farm 觀察

### 證據來源與限制

- 來源：Google Play 商店頁面的官方截圖兩張（直向 1242×2208、橫向 2208×1242），在瀏覽器中放大檢視。沒有下載、沒有存進專案。
- 開發者是 GAME START LLC。【觀察，商店頁面】
- 限制：商店截圖是把遊戲畫面放大後的結果，邊緣有一圈混色。原始資產檔沒有看過，所以下面的「原生尺寸」都是推算，不是事實。
- 只看了兩張截圖，都是同一個牧場場景。室內、對話框、動畫都沒有看到。

### 量測

量測方法：把直向截圖畫進 canvas，沿著水平與垂直掃描線統計「連續同色」的長度。

- 【量測】連續長度集中在 3–4、7–8、11–12、15–16、19、23、27…，也就是大約每 3.9 個截圖像素一階。
- 【推論】一個美術像素約等於 3.88 個截圖像素。1242 ÷ 3.88 ≈ 320，所以遊戲的邏輯解析度短邊很可能是 320（直向約 320×569）。這是推算，沒有官方資料佐證。
- 【推論】3.88 不是整數，所以這張截圖是非整數倍放大，邊緣的混色就是這樣來的。遊戲實機是否也是非整數倍，無法從截圖判斷。

以下尺寸是在放大圖上用「一個美術像素約 12.6 個螢幕像素」換算，誤差約 ±1–2 格：

| 對象 | 估計大小（美術像素） | 等級 |
|---|---|---|
| 戴草帽的農夫 | 寬約 20、高約 31 | 【量測，估計值】 |
| 其中帽子加頭 | 高約 20（約佔全身三分之二） | 【量測，估計值】 |
| 身體加腳 | 高約 11 | 【量測，估計值】 |
| 外框線 | 1 格 | 【量測】 |
| 眼睛 | 每隻 1–2 格 | 【觀察】 |

### 直接觀察到的特徵【觀察】

- **外框**：每個物件的外輪廓都有 1 格的完整外框，顏色是深灰（不是純黑）。內部的分界線用該材質自己的暗色，不用外框色。
- **色階**：每種材質大約 3–4 階。草帽是淺黃 → 黃 → 橄欖色；木頭是淺橘 → 橘棕 → 深棕。暗部的色相有偏移（黃色的暗部偏綠褐），不是單純變黑。
- **陰影**：每個角色、動物、樹的腳下都有一塊深綠色的落影，單色、沒有外框、形狀簡單。
- **亮部**：帽頂、屋頂、木頭都有小面積的亮色塊，不是整面漸層。
- **視角**：俯視角度偏高。看得到屋頂的頂面與建築的正面；人物看得到帽頂，臉只露出兩三列。
- **比例**：人物是大頭短身。動物與人差不多大，樹比人略高，穀倉大約三個人寬。比例是為了好辨認，不是照實際大小。
- **材質**：木頭用橫向木紋加圓形年輪端面；屋頂用直條明暗表現波浪板；水面是平塗加一兩條亮線。
- **細節分布**：細節集中在臉、帽子、手上拿的東西；草地是大面積平塗，只有零星小花與邊緣的碎形。
- **遮擋**：畫面下方的物件蓋住上方的物件（農夫擋住穀倉的門）。
- **介面**：底部選單是木板與橘色面板，用同一套外框與色階。

### 推論【推論】

- 物件應該是依畫面的 y 座標排序繪製，所以下方蓋住上方。
- 整體顏色數量有限，各材質共用色階，因此不同物件放在一起仍然一致。
- 光源方向無法只靠兩張圖確定。帽頂的亮點偏上方，落影在正下方，看起來接近「頂光」。

### 沒有看到、不下結論的項目【未驗證】

- 走路、工作等動畫的影格數與節奏。
- 室內家具（椅子、桌子、床、櫃子）的畫法。這款遊戲的截圖裡沒有。
- 金屬、布料、石頭的材質畫法（只看到木頭、草、水、少量布料）。
- 原始圖塊大小、圖集格式、實際使用的調色盤。

## 第三部分：其他參考資料

只列出讀過原文的內容。

### Slynyrd Pixelblog（Raymond Schlitter）

- 第 35 篇，俯視室內：採用 3/4 俯視投影，圖塊是 16×16，家具畫在 16×16 的格線內，方便與環境接合並拆成圖塊。樓梯欄杆放在比樓梯高一層的圖層。【觀察，原文】
  原文沒有說明：人物相對圖塊的大小、家具頂面與正面的比例、光源方向、外框與陰影畫法。【未驗證】
- 第 1 篇，調色盤：用 HSB 建色階，依亮度排列；亮度越高、飽和度要降低；避免高飽和加高亮度；色相隨亮度偏移。作者的例子是每條色階 9 個色、相鄰色相差 20 度，並說 20 度大約是上限。【觀察，原文】
- 第 47 篇，極小像素：以 8×8 圖塊為基礎；細節必須取捨，只保留能辨認的部分；動畫每格最少移動 1 個像素，幾個影格就是一個完整步伐；落影另外一層；建議不要過度刻畫。【觀察，原文】

### 瀏覽器的像素縮放（MDN）

- `image-rendering: pixelated`：先用最近鄰放大到最接近的整數倍，再平滑縮放到最終大小。`crisp-edges`：用最近鄰這類保留邊緣的演算法，不模糊。整個屬性自 2020 年 1 月起為各瀏覽器普遍支援，但個別值的支援程度可能不同。【觀察，原文】
- canvas 的 `imageSmoothingEnabled` 預設為 `true`，設為 `false` 可保持像素銳利，自 2017 年 4 月起普遍支援。【觀察，原文】
- SVG 的 `shape-rendering="crispEdges"`：瀏覽器「可能」關閉反鋸齒、「可能」把邊緣對齊裝置像素，行為由瀏覽器決定。【觀察，原文】
  【推論】所以本專案應該維持整數倍縮放，不依賴瀏覽器幫忙修邊。

### 搜尋摘要中的說法（沒有讀到原文）【未驗證】

- 「16×16 的小圖只需要 3 階色階」「選擇性外框在 32×32 以上才明顯」。這些與上面的觀察不衝突，但只來自搜尋摘要，不當作依據。

## 第四部分：給本專案的方向【提案】

詳細規格在 `03-style-specification.md`，這裡只列方向：

1. 全場景使用同一個像素密度，家具也畫在格線上。
2. 角色放大到大約 24×32 格，才有空間容納外框、三階明暗與表情。
3. 每種材質一條有色相偏移的色階，全場共用一份調色盤。
4. 外輪廓 1 格深色外框，內部線條用材質暗色。
5. 場景改成 3/4 俯視：家具有頂面與正面，物件依 y 排序，腳下有落影。
6. 不照抄 Tiny Pixel Farm 的角色、動物或建築造型；只採用上面這些通用技法，題材維持本專案的冒險者公會。
