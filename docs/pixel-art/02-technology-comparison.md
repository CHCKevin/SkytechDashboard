# 02 產生技術比較

日期：2026-11-17
標記方式與 `01-style-research.md` 相同：【觀察】【推論】【提案】【未驗證】。

## 先決條件（來自本專案，會直接淘汰某些做法）

1. 角色必須在瀏覽器即時產生：成員是搜尋後才加入，事先不知道有誰。
2. 同一個使用者編號永遠得到同一個造型。
3. CSP `default-src 'self'`：執行時不能連外部服務，不能用 `data:`／`blob:` 圖片。
4. 專案沒有執行期依賴，原則是簡單優先。
5. 使用者一個人維護，沒有專職美術。

## 四種做法

### A. 純程序產生

用程式畫出每一個像素：幾何形狀、雜訊、規則式上色。

- 優點：完全可重現、可自動化、沒有授權問題、可以在瀏覽器跑。
- 缺點：有機的形狀（臉、頭髮、植物）很難只靠規則畫得好看。品質上限取決於規則寫得多細。
- 適合：木紋、磚、地板這類有規律的材質；明暗與外框這類可以用規則描述的後處理。

### B. AI 產生後再做像素化處理

- 【觀察，非廠商文章】一般影像模型畫的是「像素畫的圖片」：格線不一致、邊緣模糊、顏色數量過多。作者的處理流程是偵測格線大小 → 對齊裁切 → 調色盤量化 → 以區塊主色縮小。
- 【觀察，廠商自己的說明】SpriteCook 說明模型在約 1024×1024 作畫再縮小，重畫新姿勢時可能換成不同的格線大小。這是廠商對自家產品失敗情形的描述。
- 【觀察，廠商行銷頁】
  - PixelLab：提供骨架動畫、4／8 方向、補畫、風格一致的產生，有 API。條款寫使用者保有產出內容的所有權，可用於任何用途，但不得拿去訓練其他模型，並要求遵守 Open RAIL-M 授權條款。價格頁面沒有讀到。
  - Retro Diffusion：宣稱輸出在真正的像素格線上、可鎖定調色盤、可由一張圖產生 4–16 格動畫，有 API。首頁列出每張約 0.03–0.18 美元，並在常見問題中說使用者擁有輸出、可商用。完整條款頁沒有讀到內容。
- 【未驗證】沒有找到獨立的、比較各工具「跨影格角色一致性」的測試。廠商的一致性說法不當作依據。
- 【未驗證】AI 產出能否受著作權保護：美國著作權局 2025 年 1 月 29 日發表了第二部分報告（著作權局網頁）。報告 PDF 取回後無法轉成文字閱讀，這裡不轉述結論。
- 本專案的硬限制：不能在執行時使用（先決條件 1、3），只能在開發時當作起稿工具。

### C. 可組合的部件與樣板

事先畫好部件（身體、頭、髮型、衣服、配件、家具樣板），執行時依規則疊圖層、換顏色。

- 【觀察】本專案現在就是這個做法的最小版本（`BODY` 加 `HAIRS`、`HATS` 覆寫）。
- 【觀察，專案文件】Universal LPC 角色產生器是這個做法的大型實例：影格 64×64，每個選項最多 9 個圖層，依 z 值由小到大繪製。其美術素材混用 CC0、CC-BY、CC-BY-SA、OGA-BY、GPL，除 CC0 外都要標示作者，CC-BY-SA 與 GPL 的衍生作品要用相同授權。
- 優點：品質由手繪部件決定，上限高；跨影格一致（每個部件各畫各的影格）；可重現；可在瀏覽器跑。
- 缺點：部件要有人畫；變化數量等於部件數量的組合。

### D. 混合：部件組合 + 程序上色 + AI 輔助起稿

- 形狀來自手繪或 AI 起稿後人工修過的樣板（C）。
- 顏色、明暗、外框、木紋、落影由程式依風格規格統一處理（A）。
- AI 只在開發時用來產生草稿，經過正規化與人工修正後才變成樣板（B），而且是選用的。

## 建議【提案】

採用 **D，並且以 C 為主體**：

1. 形狀用「字元格樣板」表示（延續現在 `sprite.js` 的寫法）。樣板是純文字，放在版本控制裡，可以直接用編輯器修改。
2. 樣板只標「材質與明暗階」，不寫死顏色。顏色、外框、落影由引擎依風格規格套用，所以風格一致是規則保證的，不是靠人記得。
3. 木紋、地板這類規律材質用小型程序規則產生。
4. AI 介面保留為選用、只在開發時使用，第一版不做。理由：需要付費帳號與金鑰、一致性沒有獨立證據、產出仍要人工修成樣板。
5. 不使用 LPC 素材。它的 64×64 規格與授權義務都不適合這個專案；只借用「圖層加 z 值」的概念。

理由整理：

- B 單獨使用被先決條件 1、3 淘汰。
- A 單獨使用做不出 Tiny Pixel Farm 等級的角色，因為那種品質來自人為設計的形狀。【推論】
- C 是現有程式的自然延伸，改動最小。
- D 在 C 之上多的只有「用規則套色」，這正好解決現況中密度與明暗不一致的問題。

## 實作語言：為什麼不是 C#/.NET【提案】

需求文件希望在相容時優先用 C#/.NET。這個專案不相容，理由如下：

- 角色必須在瀏覽器裡即時產生，瀏覽器端只能是 JavaScript（或 WebAssembly）。
- 開發工具（匯出 PNG、驗證、預覽）如果用 C#，同一套產生邏輯就要寫兩份，或者把 .NET 編成 WebAssembly 載入。兩者都明顯比現在複雜，而且專案裡完全沒有 .NET。
- 用純 JavaScript ES 模組，同一份引擎可以同時給瀏覽器、Node 工具、Vitest 測試使用。

結論：引擎用不依賴 DOM、不依賴 Node 的純 JavaScript 模組；它不知道 Svelte、SVG 或 PNG 的存在，符合「產生引擎獨立於繪製與介面框架」的要求。
